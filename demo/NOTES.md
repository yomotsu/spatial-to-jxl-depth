# デモ開発メモ

## 表示方式

- 初期値は「深度メッシュ（3D）」。設定から「深度ワープ（2D）」へ切り替えられる。
- 方式、視差の強さ、カーソルまたは端末の傾き、深度表示は同じ読み込み画像で比較できる。
- メッシュはWebGL 1で動き、深度画像から最大約768分割の格子を作る。16ビット未満のインデックスに収まるようタイルに分けているため、`OES_element_index_uint` に依存しない。
- メッシュは選択時に作成し、画像を差し替えるとGPUバッファーを破棄する。写真にない背景は生成できず、隙間が開いた場所は三角形が引き伸ばされる。
- 深度なしの画像では方式を選べない。深度表示後に色画像へ戻すと、選択中の描画方式へ戻る。

## JXL読み込み

- 色画像と深度抽出は同時に始め、色のWASMデコードと深度のJavaScriptデコードには別々のWeb Workerを使う。各ワーカー内でデコーダーを一度準備して再利用する。
- ネイティブ色デコードが使える場合は `createImageBitmap()` を使い、深度抽出と並行する。使えない場合は色のWASMデコーダーもワーカーで動かす。
- ファイル選択やドラッグ開始時にワーカーを起動する。読み込み済み画素は転送して、巨大なバッファーのコピーを避ける。
- 外部の深度ファイルを別に指定したときは、JXLに内蔵された深度の抽出を省略する。
- ワーカーを作れない環境ではメインスレッドへフォールバックする。この経路では並列処理による応答性の改善は得られない。
- ワーカーURLは `app.js` からの相対URLで作る。モジュールの相対importも各ファイル自身を基準に解決する。

## 速度の目安

Chromium 156で640×480の人工的な深度付きJXLを使い、色画像のWASMデコードと深度抽出が完了するまでを各3回測定した。メインスレッドで順番に処理する従来経路は **中央値278ms**、ワーカーで並列に処理する経路は **中央値178ms** で、約36%短縮した。両経路の画素出力は一致した。

これはワーカー起動後の人工画像での比較値。初回のワーカー起動、異なる画像サイズ、実写真、端末性能、GPUへの画像転送やメッシュ生成を含む全体時間は別に測る必要がある。実際の短縮幅は環境で変わる。

## 確認方法

```sh
npm test
```

テストは並列起動とワーカー再利用、ネイティブデコードとの並行、深度の失敗、外部深度の読み込み、ワーカー起動失敗時のフォールバック、深度の向きと正規化を確認する。ブラウザー上では人工深度画像でも、両方式の切り替え、視点移動、深度表示、画像差し替えを確認した。
